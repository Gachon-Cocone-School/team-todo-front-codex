# 프론트엔드 테스트 케이스

## 1. 목적과 범위

이 문서는 [`plan.md`](./plan.md)의 인수 기준을 확인하기 위한 테스트 시나리오를 제공합니다. TODO 목록·상세·생성·수정·삭제, 필터·페이지 이동, 설정 화면의 테마 선택, 오류 및 반응형 동작을 다룹니다.

브라우저에서 직접 수행하는 수동 테스트를 필수로 포함합니다. 자동 테스트는 단위·컴포넌트·API 클라이언트 테스트로 구성합니다. **Playwright를 이용한 E2E 테스트는 범위에서 제외합니다.**

## 2. 테스트 환경과 준비

- 프론트엔드 개발 서버를 실행하고 `.env.local`의 `API_BASE_URL`이 `http://127.0.0.1:8000`을 가리키는지 확인합니다.
- 백엔드와 SQLite 데이터베이스를 실행합니다. 로그인은 필요하지 않습니다.
- 삭제 API는 데이터를 영구 삭제하므로 전용 로컬 개발 DB에서 테스트합니다. 공유·운영 데이터는 사용하지 않습니다.
- 프론트엔드는 페이지마다 20개를 표시하므로 페이지 이동을 확인하려면 TODO를 21개 이상 준비합니다. 백엔드 API의 기본 `limit`은 50입니다.
- 앱 화면 경로는 TODO 목록(`/`), TODO 상세(`/todos/{id}`), 설정(`/settings`)입니다.

## 3. 수동 테스트 시나리오 (필수)

아래 시나리오는 실제 브라우저에서 직접 확인합니다. 결과를 `통과` 또는 `실패`로 기록하고, 실패하면 브라우저·화면 크기·재현 절차도 남깁니다.

| ID   | 시나리오            | 사전 조건                                                        | 수행 절차                                                                  | 기대 결과                                                                                                                                           |
| ---- | ------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| M-01 | 기본 진입 화면      | 프론트엔드와 백엔드 실행                                         | 앱 기본 주소로 접속                                                        | 테마 선택 화면이 아니라 TODO 목록이 표시된다. 인증을 요구하지 않는다. 현재 저장된 테마가 적용된다.                                                  |
| M-02 | TODO 생성           | 목록 화면 진입                                                   | 제목과 선택 항목(설명, 담당자, 마감일, 우선순위, 상태, 태그)을 입력해 생성 | 생성 폼이 닫히고 새 TODO가 목록에 나타난다. 상세 화면에서 저장된 필드와 일치한다. 기본 우선순위/상태는 각각 `MEDIUM`/`TODO`다.                      |
| M-03 | 생성 입력 검증      | 목록 화면 진입                                                   | 제목을 비워서 제출한 뒤, 공백만 입력해 다시 제출                           | 제출이 막히거나 필드 오류가 명확히 표시된다. 잘못된 요청으로 TODO가 생성되지 않는다.                                                                |
| M-04 | 목록 필터           | 서로 다른 상태·담당자·우선순위·마감일·태그를 가진 데이터 준비    | 각 필터를 하나씩 적용하고, 이후 여러 필터를 함께 적용                      | 결과가 선택한 조건과 일치한다. 필터 변경 후 페이지가 첫 페이지로 돌아가며 이전 필터 결과가 섞이지 않는다. 필터 해제 시 전체 목록으로 복원된다.      |
| M-05 | 페이지 이동         | 목록 항목이 20개 초과                                            | 다음 페이지로 이동한 뒤 이전 페이지로 이동                                 | 각 페이지가 중복 없이 이어지고 항목 범위가 표시된다. 마지막 페이지에서 더 이동할 수 없으며 필터 변경 시 첫 페이지로 돌아간다.                       |
| M-06 | TODO 상세 조회      | 목록에 TODO가 한 개 이상 존재                                    | 목록 항목을 열기                                                           | 제목, 설명, 담당자, 마감일, 우선순위, 상태, 태그, 생성/수정 시각이 API 값과 일치한다. 선택적 값이 없으면 깨진 UI 대신 적절한 빈 값 표현을 사용한다. |
| M-07 | TODO 수정           | 수정 가능한 TODO 존재                                            | 상세 화면에서 제목과 한 개 이상의 필드를 바꾸고 저장한 뒤 새로고침         | 상세 화면에 변경 내용이 표시된다. 목록으로 돌아가도 변경된 값이 보이며, 수정하지 않은 필드는 유지된다.                                              |
| M-08 | nullable 값 비우기  | 설명·담당자·마감일 중 하나 이상이 설정된 TODO 존재               | 해당 값을 비운 뒤 저장                                                     | 백엔드에 null이 반영되고 새로고침 후에도 빈 값으로 표시된다. 태그 전체 삭제는 UI에서 지원하는 경우 빈 목록으로 저장된다.                            |
| M-09 | TODO 삭제 및 취소   | 삭제 가능한 TODO 존재                                            | 삭제를 시작해 확인 대화상자에서 취소                                       | TODO가 삭제되지 않고 목록과 상세 데이터가 그대로 유지된다.                                                                                          |
| M-10 | TODO 삭제 확정      | 삭제 가능한 전용 테스트 TODO 존재                                | 삭제를 시작해 확인 대화상자에서 확정                                       | TODO가 목록에서 사라지고 이후 상세 조회는 찾을 수 없음 상태를 표시한다. 다른 TODO에는 영향이 없다.                                                  |
| M-11 | 설정에서 테마 전환  | 앱에 접속                                                        | 설정 화면에서 Productivity 테마를 선택한 후 목록·상세로 이동               | 설정 화면에서만 선택하는 별도 흐름이 제공된다. 선택한 테마가 각 화면에 일관되게 적용된다.                                                           |
| M-12 | 테마 저장 및 복원   | 테마 전환 완료                                                   | 새로고침하고, 다른 화면으로 이동한 뒤 앱을 다시 연다                       | 마지막으로 선택한 테마가 유지된다. 앱 진입은 계속 TODO 목록이다.                                                                                    |
| M-13 | 두 테마의 주요 화면 | 테스트 데이터 존재                                               | 두 테마를 번갈아 선택하며 목록·상세·설정 화면을 확인                       | 두 디자인 가이드의 색상·타이포그래피·표면 스타일이 구분되어 적용된다. 텍스트와 상태 배지의 대비 및 가독성이 유지된다.                               |
| M-14 | 모바일 화면         | 브라우저 모바일 뷰 또는 실제 모바일 기기                         | 목록·상세·설정 화면을 확인하고 생성·수정 동작을 수행                       | 가로 넘침 없이 주요 정보를 확인할 수 있다. 버튼과 입력이 터치하기 쉽고 핵심 동작을 완료할 수 있다.                                                  |
| M-15 | 로딩·빈 목록        | 빈 DB 또는 필터 결과가 없는 조건                                 | 목록에 진입하거나 결과가 없는 필터를 적용                                  | 요청 중 로딩 표시가 나타나고, 완료 후 빈 상태 안내가 표시된다. 오류와 빈 결과를 혼동하지 않는다.                                                    |
| M-16 | 백엔드 오류와 복구  | 프론트 실행 중 백엔드를 잠시 중지할 수 있음                      | 목록 요청을 발생시켜 오류를 확인한 뒤 백엔드를 복구하고 재시도             | 원인을 이해할 수 있는 오류 상태가 표시된다. 로딩이 멈추지 않거나 빈 목록으로 오인되지 않는다. 재시도 후 정상 데이터를 표시한다.                     |
| M-17 | 존재하지 않는 TODO  | 존재하지 않는 ID를 사용하거나 테스트 TODO 삭제 후 상세 주소 접속 | 해당 상세 화면을 연다                                                      | 예외 화면이나 무한 로딩 대신 찾을 수 없음 상태와 목록으로 돌아가는 방법을 제공한다.                                                                 |
| M-18 | API 주소 설정       | `.env.local`에 `API_BASE_URL` 설정                               | 설정값으로 프론트엔드를 재시작하고 목록을 요청                             | 브라우저의 `/api/backend/todos` 요청이 설정한 백엔드의 `/api/v1/todos`에 도달한다. 기본 설정에서는 `127.0.0.1:8000`을 사용한다.                     |

## 4. API 계약 및 입력 검증 확인

백엔드 OpenAPI 계약 기준으로 화면과 요청이 일치하는지 확인한다.

| ID     | 확인 항목         | 기대 결과                                                                                                                                                                                         |
| ------ | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API-01 | 상태 및 우선순위  | 상태는 `TODO`, `IN_PROGRESS`, `DONE`; 우선순위는 `LOW`, `MEDIUM`, `HIGH`만 전송하고 올바른 라벨로 표시한다.                                                                                       |
| API-02 | 필수 제목 및 길이 | 제목은 trim 후 1~200자 범위로 검증한다. 공백만 입력할 수 없다.                                                                                                                                    |
| API-03 | 선택 텍스트 길이  | 설명은 최대 5000자, 담당자는 최대 100자 제한을 사용자에게 안내한다.                                                                                                                               |
| API-04 | 태그              | 태그는 앞뒤 공백을 제거하고 빈 값을 허용하지 않는다. 중복은 정규화되어 중복 저장되지 않는다. 전체 제거 동작은 빈 배열을 보낸다.                                                                   |
| API-05 | 날짜              | 마감일은 `YYYY-MM-DD` 형식으로 전송한다. 목록 날짜 범위의 시작일이 종료일보다 늦으면 요청 전에 오류를 표시한다.                                                                                   |
| API-06 | 부분 수정         | 변경한 필드만 `PATCH`로 전송한다. 생략한 필드는 유지되고 설명·담당자·마감일은 명시적으로 비울 수 있다.                                                                                            |
| API-07 | 목록 요청         | 상태·담당자·우선순위·마감일 범위·태그 필터와 `limit`/`offset`이 쿼리 파라미터로 전송된다. 프론트엔드는 `limit=20`을 사용하며, 백엔드 API의 허용 범위는 1~100·기본값은 50·`offset` 기본값은 0이다. |
| API-08 | 오류 응답         | 422 검증 오류, 404 없는 항목, 연결 실패가 사용자에게 구분 가능한 메시지로 표시된다. 내부 스택이나 SQL 정보는 노출하지 않는다.                                                                     |

## 5. 비 E2E 자동화 검증

자동 테스트는 Playwright E2E 대신 다음 단위로 구성합니다.

- API 요청 함수의 URL, 쿼리 파라미터, JSON body, 상태 코드 처리
- 입력 폼의 필수값·길이·enum·날짜 검증
- 필터/페이지 상태 변환과 테마 저장·복원 로직
- 목록/상세/설정 컴포넌트의 로딩·빈 상태·오류·성공 표시
- 타입 검사, lint, 빌드 및 필요한 컴포넌트 테스트

백엔드 연동은 3장의 수동 시나리오로 확인합니다. 이 문서는 Playwright E2E 케이스나 실행을 요구하지 않습니다.
